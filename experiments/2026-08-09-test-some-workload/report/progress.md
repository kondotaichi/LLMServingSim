# Method Fix 検証進捗

## 1. PP2とKV migrateの組み合わせ

### 均等負荷での否定的結果

従来の300リクエストのワークロードでは、負荷を12x、15x、20x、30xへ
引き上げても、PP2でredirectは一度も発生しなかった。平均TTFTは2165 msから
2996 msへ悪化したが、すべてのリクエストがlocalで処理された。

12xで`max_num_seqs`を128から32へ下げた場合もredirectは0件であり、p99 TTFT
だけが11.4秒まで悪化した。

この結果は、到着時間軸の圧縮だけではPP2とKV migrateの組み合わせを検証できない
ことを示す。全GPUがほぼ均等に混雑すると、home instanceが処理できなくなる時点で
他のinstanceにも余剰capacityがなく、redirect先が見つからない。また、デフォルト
設定では300件という総リクエスト数自体がPP2全体のsequence capacityを超えない。

### 条件を揃えたhotspot機構プローブ

次の条件を事前に固定してプローブを実施した。

- 12x負荷、300リクエスト
- 6 logical instanceのPP2構成
- `max_num_seqs=32`
- instance 0へ50%のリクエストを決定論的に配置
- 残り50%を他の5 instanceへ均等配置
- cold/KVの両方で、全候補からcapacity pressure最小の宛先を選択

cold対照用として`NEAREST_CAPACITY_MULTI_PRESSURE_COLD_RESERVE`を追加した。
このポリシーはKV版と同じ候補列挙・pressure-based選択を行い、redirectされた
prefixをKV移送せず再計算する点だけが異なる。

| 指標 | PP2 cold | PP2 KV | KVによる改善 |
|---|---:|---:|---:|
| Redirect数 | 92/300 | 92/300 | 同一リクエスト集合 |
| 平均TTFT | 4104.8 ms | 3515.7 ms | 589.1 ms（14.4%） |
| p50 TTFT | 2733.4 ms | 2044.0 ms | 689.4 ms |
| p95 TTFT | 12086.6 ms | 10947.2 ms | 1139.4 ms |
| p99 TTFT | 15509.2 ms | 15509.2 ms | 0 ms |
| Redirectリクエストの平均KV移送時間 | 0 ms | 203.3 ms | 追加コスト |

両方式でredirectされた92件は完全に同一だった。その92件に限定したpaired比較では、
KV migrateによる平均TTFT改善は325.1 msだった。全300件での改善がこれより大きい
のは、KV再利用による処理時間短縮が後続のlocalリクエストのqueueも間接的に緩和した
ためである。

一方、p99はまったく改善していない。KV migrateは平均およびp50/p95を改善するが、
最悪tailを支配する別のボトルネックは解消していない。

以上から、局所的な負荷偏りと移送先の余剰capacityが同時に存在する場合、PP2と
KV migrateを組み合わせることには明確な効果がある。ただし、50% hotspotや
`max_num_seqs=32`が実運用上の最適設定であることは意味しない。正式なPP×KVの
交互作用を求めるには、PP1の対照実験と複数seedでの反復が必要である。

## 2. Proactive KV prewarmのワークロード妥当性

従来の本郷300件ワークロードは、288ユーザー／セッションに対して再訪が12件しか
なく、再訪率は4%だった。時系列を前半・後半に分けると、評価区間となる後半150件
の再訪は4件しかない。このデータでは頻出ユーザー予測を有意に評価できない。

2000件版を切り捨てずに再生成したワークロードは次の性質を持つ。

- 1129ユーザー／セッション
- 871件の再訪、再訪率43.55%
- 本郷ワークロードへの変換後は全リクエストに再利用可能prefixが存在
- peak 20xで再訪間隔p50 0.97秒、p95 4.11秒

したがって、総リクエスト数を固定すること自体が誤りだったわけではない。主な問題は
先頭300行だけを採用し、セッション継続の大部分を失ったことである。今後のMethod C
比較では、時間窓を主要な終了条件にするか、セッションを壊さないサンプリングを行い、
さらに時系列に沿って観測区間と評価区間を分離する必要がある。

現行の`recent_count`は比較baselineとして扱う。改善候補は次のとおりである。

- 過去のアクセスほど重みを減らす指数減衰付きrecency score
- 再訪score、再利用KV量、回避可能な移送時間を組み合わせたexpected utility
- 次回アクセスが来ないprewarmエントリの明示的な有効期限

減衰半減期や有効期限などのパラメータは観測区間だけで決め、分離した評価区間では
一度だけ評価する。これにより、Method Cが勝つようにワークロードやパラメータを
後付けで選ぶことを避ける。
